Software Design: Web/Desktop

Software Design - kFleet Management System

Architecture Orientée Services pour une Flotte BTP

1. Architecture Globale

Style : Microservices + Événements
Patterns Clés : CQRS, Event Sourcing (pour les données critiques)
Stack :

  • Backend : Rust (Axum) + PostgreSQL
  • Frontend : React PWA (Progressive Web App)
  • Mobile : React Native
  • Bus Événements : Redis Streams / Apache Kafka / RedPanda

3. Services Principaux

a) Asset Service

Responsabilités :

  • Gestion du cycle de vie des machines
  • Tracking temps réel (statut ON/OFF/maintenance)
  • Gestion des documents techniques (assurances, contrôles)

API Clés :

  • POST /assets : Ajouter une machine
  • GET /assets/{id}/status : Statut temps réel
  • PUT /assets/{id}/documents : Mettre à jour documents

b) Contract Service

Workflow Automatisé :

  1. Génération devis → 2. Signature électronique → 3. Facturation

Intégrations :

  • Webhooks Docuware (statuts signatures)
  • Sync bidirectionnelle avec Odoo

c) Planning Service

Fonctionnalités :

  • Réservation self-service des véhicules
  • Algorithmes d’optimisation :
fn optimize_assignement(vehicles: Vec<Vehicle>, drivers: Vec<Driver>) -> HashMap<Vehicle, Driver> {  
    // Logique métier pour matching compétences  
}
  • Conflits détectés via événements

d) Reporting Service

Data Flow :

  1. Collecte événements → 2. Agrégation TimescaleDB → 3. Génération PDF/Excel

KPI Principaux :

  • Taux d’utilisation machines
  • Coût moyen par heure/machine

6. Stratégie de Fiabilité

a) Désynchronisation Contrôlée :

  • Pattern Saga pour transactions distribuées (ex: réservation machine → contrat)

b) Monitoring :

  • Dashboard Prometheus/Grafana :
    • Latence des microservices
    • Taux d’erreurs intégrations
  • Alertes Slack sur :
    • Disponibilité < 99%
    • Sync Odoo > 1h retard

c) Disaster Recovery :
- Réplication multi-AZ (AWS)
- Backups automatisés :
- Bases OLTP : RPO 15 min
- Data warehouse : RPO 24h

8. Évolutivité Prévisionnelle

Scale Horizontale :

  • Jusqu’à 500 machines : 2 instances Rust
  • +500 machines : Ajout de nodes Kubernetes
  • Pic de requêtes : Cache Redis (30% gains perf)

Avantages Rust :

  • 1 instance = 10k req/s (vs 2k en Python/Node)
  • Consommation mémoire ÷ 3 vs JVM

Ce design optimise :

✅ Maintenabilité : Découpage microservices
✅ Performance : Stack Rust + PostgreSQL
✅ Adaptabilité : Événements pour intégrations futures
✅ UX Terrain : PWA fonctionnelle offline

Les choix techniques permettent une rentabilité accrue grâce aux coûts d’infra réduits, crucial pour le marché Malagasy.

T:

Nous allons concevoir une architecture logicielle modulaire pour le système de gestion kFleet, sans entrer dans les détails d’implémentation.

L’accent est mis sur la structuration des composants et leurs interactions.

Architecture Générale

Style Architectural : Microservices (bien que monolithique modulaire soit possible avec Rust+Axum)
Base de Données : PostgreSQL (avec TimescaleDB pour les séries temporelles de tracking)
Communication : REST/GraphQL pour les APIs externes, gRPC pour les communications internes entre services

Description des Services Principaux

1. Asset Service

  • Responsabilités :
    • Gestion du catalogue machines (CRUD)
    • Suivi état en temps réel (connecté au flux IoT)
    • Gestion des documents liés (assurance, contrôles techniques)
  • Entités Clés : Machine, MachineDocument, MachineStatus
  • Intégrations :
    • IoT Ingestion (réception des données GPS/état)
    • Docuware (stockage documents)

2. Contract Service

  • Responsabilités :
    • Cycle de vie des devis/contrats (brouillon → signé → terminé)
    • Génération automatique de contrats basés sur des templates
    • Intégration signature électronique
  • Entités Clés : Quote, Contract, TariffGrid
  • Intégrations :
    • Odoo (synchro devis NOTE: Client pas sûr. Docuware Only?)
    • Docuware (signature/storage)

3. User Service

  • Responsabilités :
    • Gestion des utilisateurs (clients, employés, administrateurs)
    • Authentification/autorisation (JWT/OAuth2)
    • Profils et permissions
  • Entités Clés : User, Role, Permission

4. Planning Service

  • Responsabilités :
    • Réservation des ressources (machines, opérateurs)
    • Optimisation des affectations
    • Gestion des conflits
  • Entités Clés : Reservation, Assignment, ResourceConflict
  • Algorithmes Clés :
    • Heuristiques d’optimisation (ex: affectation machine/opérateur)
    • Détection de conflits en temps réel

5. Reporting Service

  • Responsabilités :
    • Génération de rapports (PDF/Excel)
    • Tableaux de bord personnalisables
    • Analytics prédictifs (via ML)
  • Sources de Données :
    • PostgreSQL (données transactionnelles)
    • TimescaleDB (données temporelles)
    • Data Warehouse (pour l’historique long)

Flux Data Critique

Flux 1 : Mise à Jour État Machine

  1. Capteur IoT → IoT Ingestion (via MQTT/HTTP)
  2. IoT Ingestion → Asset Service (gRPC)
  3. Asset Service :
    • Met à jour le statut dans PostgreSQL
    • Publie un événement “MachineStatusChanged”
  4. Planning Service & Frontend (écoutent l’événement) → mise à jour UI

Flux 2 : Création de Contrat

  1. User Frontend → Contract Service (création devis)
  2. Contract Service :
    • Génère le PDF (template LaTeX/PDFreactor)
    • Appel Docuware API pour stockage
    • Met à jour Odoo via webhook
  3. Docuware → notifie utilisateur pour signature
  4. Signature → webhook → Contract Service → marque contrat comme signé

Décisions Clés

  1. Synchronisation des Données :
    • Pattern : Event-Driven Architecture (messages asynchrones via Redis Streams/NATS)
    • Avantage : Découplage, résilience, montée en charge
  2. Gestion des Documents :
    • Stockage : Docuware (externalisé) + metadata dans PostgreSQL
    • Indexation : Elasticsearch pour la recherche full-text
  3. Sécurité :
    • Authentification : JWT avec refresh tokens
    • Autorisation : RBAC (Role-Based Access Control)
    • Chiffrement : AES-256 au repos, TLS 1.3 en transit
  4. Monitoring :
    • Outils : Prometheus/Grafana + Sentry
    • Métriques : Latence des APIs, taux d’erreur, saturation

Schéma de Base de Données (Core)

User (id, email, password_hash, role, ...)
Machine (id, serial_number, model, status [ENUM], gps_device_id, ...)
MachineDocument (id, machine_id, doc_type [ENUM], expiry_date, file_url)
Contract (id, client_id, start_date, end_date, status [DRAFT/SIGNED/...], pdf_url)
Quote (id, contract_id, amount, status [PENDING/ACCEPTED/...])
Reservation (id, machine_id, operator_id, start_time, end_time, purpose)

Évolutivité

  • Scale Horizontal : Chaque service déployable indépendamment (Docker/K8s)
  • Cache : Redis pour les données fréquemment lues (ex: liste machines)
  • Async Processing : Arrière-plans lourds (génération rapports) via queues (RabbitMQ)

Ce design assure une séparation claire des responsabilités tout en permettant des intégrations flexibles avec les systèmes existants. La robustesse de Rust garantit la fiabilité des traitements critiques comme la gestion des contrats ou le suivi temps réel.
